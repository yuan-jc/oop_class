## 2. 测试目标

脚本需要支持两种互补的测试。

第一种是固定负载测试：用户指定消息大小、每秒发送数量、运行时长和订阅者数量，测量该负载实际产生的通信流量以及送达情况。

第二种是限带宽测试：在相同负载下限制服务端到订阅者的下行链路，观察带宽不足时是否出现排队、吞吐下降、延迟上升、重复或截止时间内未送达。

核心问题如下：

1. 发送一条业务消息实际消耗多少字节？
2. 总流量中，业务内容、协议元数据、响应和后台查询各占多少？
3. 发送频率和订阅人数增加时，流量如何变化？
4. 指定带宽能否支撑目标发送频率？
5. 超过带宽后，消息能否在排空期内全部送达，延迟如何变化？

本测试将“带宽上限”“实际吞吐量”“累计传输量”分别统计，不用同一个“带宽”指标混称三者。

## 3. 已确认的通信实现

### 3.1 订阅与发布

客户端通过 Netty 建立 TCP 连接。订阅请求包含应用名、键、请求 UUID、客户端回调地址和端口。服务端按应用名与键记录订阅者。

客户端 API 发布的入口为 `RippleClient.put()`，随后由 `Api.putAsync()` 创建 `PutRequest`，调用 `channel.writeAndFlush()`。

服务端网页发布的入口不同：HTTP 表单直接调用 `Node.put()`。因此，从服务端网页触发的实验不包含发布客户端到服务器的 TCP PUT 请求，不能直接代表完整的客户端发布成本。

服务端将更新转换为业务消息，经 `propagateMessage()` 去重、保存、通知订阅者，并在线程池中执行节点间同步。返回发布响应时，异步同步和下游送达可能尚未完成。

### 3.2 编码与接收

网络帧格式为：

```text
[消息体长度：4 字节][消息类型：1 字节][其余字段]
```

字符串使用 4 字节 UTF-8 字节长度加内容。当前 UUID 通过字符串编码，占 4 + 36 = 40 字节。

接收端先通过 `LengthFieldBasedFrameDecoder` 从 TCP 字节流中取出完整帧，再由 `MessageDecoder` 按消息类型解码。`MessageHandler` 选择处理器；处理器返回响应时，再经编码流水线发送。

TCP 包与 Ripple 消息不是一一对应关系：一条消息可以跨多个 TCP 段，多条消息也可以出现在同一个段中。按消息类型统计流量时，必须先完成 TCP 流重组和 Ripple 帧解析。

### 3.3 本次观察到的传播路径

```text
服务端网页 → 节点 1
                ├─ SYNC → 节点 2 ─ SYNC → 订阅客户端
                └─ SYNC → 节点 3
```

此路径是本次三节点 hashing 配置和指定主题的观察结果。其他主题、节点数或分发策略可能产生不同路径。

## 4. 已完成的预实验

### 4.1 条件

- 三个服务端 API 端口：3001、3002、3003。
- 一个订阅客户端 API 端口：5001。
- 数据：应用名 `testApp`，键 `testKey`，值 `hello`。
- 全部进程位于同一个 WSL，使用 `127.0.0.1`。
- 抓取 `lo` 回环接口，排除 Web 控制台端口。
- BPF 过滤条件：`tcp and (portrange 3001-3003 or port 5001)`。
- 空闲窗口目标时长 10 秒；发布窗口目标时长 20 秒，包含一次网页更新。
- 两次 tcpdump 均报告内核丢弃包数为 0。

### 4.2 抓包结果

| 指标 | 空闲窗口 | 发布窗口 |
|---|---:|---:|
| 目标采集时长 | 10 秒 | 20 秒 |
| PCAP 包数 | 9 | 28 |
| TCP 载荷累计字节 | 294 | 1152 |
| 抓包帧累计字节 | 888 | 3000 |
| 按目标时长计算的 TCP 载荷速率 | 29.4 B/s | 57.6 B/s |
| 按目标时长计算的抓包帧速率 | 88.8 B/s | 150 B/s |
| PCAP 文件大小 | 1056 字节 | 3472 字节 |

PCAP 文件大小包含文件头和逐包记录头，不能作为网络流量。帧累计字节由 PCAP 记录中的原始包长度求和；本次捕获长度与原始长度相同，没有发生截断。

以上平均速率采用目标窗口时长，不是以首末包时间差计算。正式脚本应保存实际抓包开始、停止与负载阶段边界，以实际观测窗口计算速率。

### 4.3 单次更新的协议成本

发布窗口观察到三组同步请求与响应：两组节点间同步，一组服务器到客户端同步。

| 内容 | 单条 TCP 载荷 | 数量 | 合计 |
|---|---:|---:|---:|
| SYNC 请求 | 142 字节 | 3 | 426 字节 |
| SYNC 响应 | 46 字节 | 3 | 138 字节 |
| 业务更新相关合计 | — | 6 条消息 | 564 字节 |

20 秒发布窗口还包含两轮后台查询，共 588 字节 TCP 载荷，因此 564 + 588 = 1152 字节。空闲窗口的一轮查询为 294 字节。

这里的 564 字节来自本次消息尺寸与路径，不是任意负载下的固定常数，也不包含 TCP/IP 头和纯 TCP ACK。

142 字节同步请求的组成如下：

| 字段 | 字节 |
|---|---:|
| 帧长度与消息类型 | 5 |
| 请求 UUID 与业务消息 UUID | 80 |
| 操作类型、应用名、键、值及长度字段 | 41 |
| 时间戳、源节点 ID、转发节点 ID | 16 |
| 总计 | 142 |

### 4.4 预实验局限

本实验没有采集订阅建立阶段，没有使用真实发布客户端发出 PUT，也没有持续负载、带宽整形或延迟分位数统计。回环接口上的帧字节不等同于物理链路占用，未包含以太网前导码、帧间间隔等物理层成本。

原始材料：`../traces/idle.pcap`、`../traces/publish.pcap`、`../traces/publish-packets.txt`。

## 5. 技术方案选择

| 方案 | 优点 | 局限 |
|---|---|---|
| 网页接口发请求并抓包 | 实现简单，可快速冒烟测试 | 不完整覆盖客户端发布协议；难以精确记录接收事件 |
| 真实 Java 客户端 + 外部 Python 调度 + tcpdump + tc | 复用项目协议，能统计真实送达和流量 | 需要负载驱动、接收事件采集和网络隔离 |
| 修改引擎加入完整统计模块 | 引擎内部指标最丰富 | 改动范围较大，容易影响被测实现 |

建议采用第二种方案。测试工具独立组织，复用已有 Java 客户端和服务端类；优先通过测试侧处理器包装或扩展点记录接收事件，避免修改业务协议。若必须修改引擎才能观测，应将该改动单独记录并验证其性能影响。

## 6. 拟定脚本架构

### 6.1 组件职责

| 组件 | 职责 |
|---|---|
| `run.sh` | WSL 命令入口、参数转交和环境提示 |
| Python 调度器 | 创建运行目录、管理进程、安排阶段、抓包、限速和汇总 |
| Java 发布驱动 | 使用真实 RippleClient，按计划发送带序号的消息 |
| Java 接收驱动 | 注册订阅，记录接收序号、时间、UUID 和处理结果 |
| 流量分析器 | 解析抓包、按连接与阶段统计字节，识别重传并输出秒级数据 |
| 说明文档与测试 | 参数语义、运行方法、边界测试和重复实验说明 |

### 6.2 网络拓扑与限速范围

拟将服务端集群和发布者放入测试网络的一侧，将订阅者放在另一侧，通过专用 veth 链路连接。服务端内部同步走其命名空间中的回环接口，跨侧通知走 veth。

默认 `--bandwidth` 表示服务器到所有测试订阅者共享的下行带宽上限，不是每个订阅者各有一个同等上限。反向响应不施加同样限速，避免下行实验混入双向瓶颈。

使用 Linux 网络命名空间隔离测试，tc 仅操作本次创建的接口。不得替换主机默认网卡或已有 Ripple 运行环境的 qdisc。

在正式实现前检测命名空间、veth 和 tc 能力。若环境不支持，应明确报错并保留不限速测试能力，不能静默忽略限速参数后输出“限速成功”。

跨地区场景还可增加 RTT、抖动和丢包参数，但第一版优先完成带宽控制；其余参数不作为本次必需范围。

## 7. 命令行参数约定

以下接口为设计示例，待脚本实现后使用：

```bash
# 固定负载：每条 value 总长度 1024 字节，每秒 100 条，发送 60 秒
./run.sh --size 1024 --rate 100 --duration 60 --subscribers 1

# 服务端到订阅者共享下行带宽限制为 512 kbit/s
./run.sh --size 1024 --rate 100 --duration 60 \
  --subscribers 1 --bandwidth 512kbit --drain-timeout 30
```

| 参数 | 语义与拟定默认值 |
|---|---|
| `--size` | value 的 UTF-8 总字节数，包含测试标记、序号和时间戳；默认 1024 |
| `--rate` | 一个发布者每秒计划提交的消息数；默认 100 |
| `--duration` | 正式发送时长，单位秒；默认 60 |
| `--subscribers` | 独立订阅客户端数量；默认 1 |
| `--servers` | hashing 服务端节点数量；默认 3 |
| `--bandwidth` | 订阅侧共享下行上限；默认不限制；`kbit` 按十进制解释 |
| `--drain-timeout` | 停止发送后的最长排空等待；默认 30 秒 |
| `--baseline-duration` | 预热完成后的空闲基线时长；默认 10 秒 |
| `--output` | 结果根目录；默认 `results/`，每次创建唯一运行目录 |
| `--seed` | 消息内容生成种子；默认固定值，记录到运行配置 |

参数应拒绝非正消息尺寸、非正频率、非正持续时间和非法带宽单位。尺寸不足以容纳测试头时明确报错。消息尺寸还应限制在实际编码帧上限以内，为应用名、UUID 等字段预留空间；当前服务端长度解码器最大帧约 1 MiB，不应直接把 value 设置到此边界。

第一版固定一个发布者。每次使用唯一应用名，所有序号使用同一键，以覆盖持续更新场景，并保证不混入用户原有订阅数据。

## 8. 消息生成与收发观测

消息 value 包含固定格式测试头、递增序号及填充内容。ASCII 测试数据便于保证字符数与 UTF-8 字节数一致；填充内容应使用可复现的伪随机数据，避免大量重复字符造成不具代表性的压缩率。

每条记录至少包含：计划发送时间、实际提交时间、发送序号、请求结果、各订阅者实际接收时间、业务消息 UUID。

不能将 `put()` 返回视为已经送达，也不能仅轮询 `get()` 的最新值统计接收量：同一键连续更新时，中间值可能在两次轮询之间被覆盖。接收统计必须在实际消息处理入口逐条采集。

发布节奏使用单调时钟的绝对时间调度，避免每次 sleep 累积漂移。记录计划速率与实际提交速率；当驱动无法跟上时记录调度迟延，不通过无上限追赶突发伪装成稳定发送。

单次 WSL 实验的跨 JVM 延迟可通过测试头中的墙上时钟时间戳测量，发送节奏和持续时间使用各进程单调时钟。报告需保留时钟来源；跨机器单向延迟必须额外说明时钟同步误差，出现负延迟时标记实验异常。

## 9. 指标定义

### 9.1 负载与送达

- `N_planned`：计划发送消息数，按频率与持续时间确定并记录取整规则。
- `N_submitted`：发布驱动实际提交的唯一序号数。
- `N_put_success`：收到成功发布响应的请求数。
- `N_received_unique`：各订阅者收到的唯一测试序号数之和。
- `N_expected = N_submitted × 订阅者数量`：以实际提交为基准的预期投递次数。
- 送达率：`N_received_unique / N_expected`，另报以成功 PUT 为基准的统计。
- 重复投递数：同一订阅者接收到的重复业务序号数量。
- 截止未送达数：在排空期限结束时仍未观察到的预期投递数。

按订阅者分别报告缺失、重复、乱序，不能用一个订阅者多收的消息抵消另一个订阅者的缺失。截止未送达不直接命名为永久丢失，因为消息可能仍在排队。

### 9.2 流量与带宽

| 指标 | 计算方式与解释 |
|---|---|
| 业务提交字节 | 实际提交的 value 字节数之和 |
| 有效送达字节 | 唯一投递对应的 value 字节数之和 |
| TCP 载荷累计字节 | 抓包中 TCP payload 长度之和，包含重传 |
| 唯一 TCP 流字节 | 按连接、方向和序列号区间去重后求和 |
| 抓包帧累计字节 | PCAP original length 求和，包含 ACK 和可见协议头 |
| 平均带宽 | `统计窗口内字节数 × 8 / 窗口秒数`，单位 bit/s |
| 秒级带宽 | 按固定 1 秒窗口汇总，同时保留首尾不足一秒的窗口长度 |
| 每次提交开销 | 业务阶段流量 / 实际提交数 |
| 每次唯一投递开销 | 业务阶段流量 / 唯一投递数 |
| 有效字节比例 | 有效送达字节 / 明确指定口径的网络字节 |

服务器内部回环流量与跨侧 veth 流量分别统计。汇总同一拓扑的流量时，每段链路仅在一个采集点计数，不能将链路两端的同一个包重复相加。

订阅、预热、后台查询和正式更新分阶段或按协议类型独立统计。基线扣除仅作为估计值，同时保留原始流量；不能用固定 29.4 B/s 扣除所有后续实验。

### 9.3 稳定性

- 发送阶段和包含排空期的送达率分别报告。
- 延迟报告 P50、P95、P99、最大值，标明样本数和分位数算法。
- 秒级实际提交速率、唯一接收速率以及调度迟延。
- 截止每秒的观测积压：已提交的预期投递次数减去已唯一接收次数；这是端到端待完成量，不等同于内核队列长度。
- 另记录 tc backlog、丢弃数、整形统计和 TCP 重传作为辅助证据。
- 记录最长无新消息时间段，结合当时是否仍有预期消息判断停顿。

测试前可以用 `消息字节数 × 发送频率 × 订阅者数量 × 8` 估算纯内容带宽下限。实际需求还包含协议元数据、响应和传输层开销，因此不能直接用此下限作为可支持速率。

## 10. 运行阶段与清理

1. 检查构建产物、依赖、端口和网络管理能力，记录环境版本。
2. 创建唯一运行目录、数据库和隔离网络，启动测试服务端与客户端。
3. 等待集群就绪和订阅成功响应；超时则终止，不带着失败订阅进入正式实验。
4. 发出探测消息，确认每个订阅者都能接收；探测消息不进入正式统计。
5. 采集空闲基线，保存该阶段边界。
6. 若指定带宽，配置测试链路的整形并保存 tc 参数与统计。
7. 按设定频率发消息，同时采集接收事件、抓包和秒级计数。
8. 停止提交后等待排空；全部预期序号到齐则结束，否则到排空期限结束。
9. 停止抓包，等待文件刷新完成，汇总结果与完整性状态。
10. 仅清理本次创建的进程、接口、命名空间和整形规则，保留原始结果文件。

异常退出、Ctrl+C、接收进程崩溃和分析失败都应触发清理，并输出失败阶段。数据库使用每次独立目录，不删除用户现有数据库。抓包丢包、截断或解码不完整时，报告标记为不完整，不能声称流量精确。

```text
├── baseline.pcap           # 空闲基线
├── traffic.pcap            # 订阅、正式发送和排空阶段流量
├── tc-stats.json           # 整形配置、队列和丢弃统计
└── logs/                   # 服务端、发布端、订阅端、抓包日志
```

每个 CSV 必须标明时间单位、字节口径和订阅者 ID。汇总中保留总分子与总分母，避免只有百分比无法复核。可后续增加图表，但原始 CSV 和 PCAP 是第一版必需产物。

## 12. 验证与实验矩阵

### 12.1 脚本正确性验收

| 场景 | 必须验证的行为 |
|---|---|
| 少量消息、不限速 | 所有序号可核对，正常环境下预期唯一投递全部到达 |
| 两个订阅者 | 各自收到完整序号，预期投递数为提交数的两倍 |
| 带宽明显高于需求 | 限速配置生效，结果与不限速基线作对照 |
| 带宽低于需求 | 输出实际限速证据、排队或未送达情况，不预设一定丢消息 |
| 停止发送后排空 | 区分发送阶段积压与排空后的最终未送达 |
| 中途 Ctrl+C | 退出后无本次遗留进程、接口和整形配置 |
| 端口占用或缺少权限 | 在负载开始前明确失败 |
| 重复、乱序、缺失合成事件 | 去重、缺失识别、统计分母和延迟计算正确 |
| 合成 PCAP 与拆分 TCP 帧 | 能处理消息拆包、合包、重传和不完整捕获 |

单元验证集中在消息尺寸、调度、序号匹配、统计和抓包分析；集成验证使用真实 Ripple、实际 tcpdump 和 tc。只有实际整形测试通过后，才能声明支持限带宽模式。

### 12.2 建议实验矩阵

- 消息大小：128 B、1 KiB、16 KiB、64 KiB。
- 发送频率：10、100、500 条/秒，超出驱动能力时记录实际值。
- 订阅者数量：1、5、10。
- 带宽：不限速，以及按实测需求约 0.5 倍、1 倍、2 倍的上限。
- 初次冒烟测试：10 秒；正式单组测试建议 60 秒，重复至少 3 次。

先做单因素实验：固定其他参数，仅改变消息大小、频率或限速值。第一轮不执行全部笛卡尔积，以免实验量过大且难以归因。

## 13. 实现优先级与待确认事项

第一阶段实现真实客户端负载、接收记录、自动抓包和不限速汇总。第二阶段实现隔离网络、tc 限速、排空与稳定性指标。第三阶段完善异常清理、多订阅者和重复实验。

尚需确认的默认边界是：是否采用本报告提出的三节点 hashing、一个发布者、可配置订阅者，以及“共享订阅下行限速”的定义。用户若要限制整个集群总流量，或分别限制每条节点间链路，应另行定义整形拓扑，不能复用一个参数而改变其含义。

本节保留初始方案边界。现有预实验本身不足以得出最大吞吐量结论；后续脚本实施与限速验证详见第 15 节，同样不将短时验收等同于完整性能基准测试。

## 15. 外部脚本实施与验收记录

### 15.1 交付结构

工具位于 `D:\Ripple\bandwidth_test`，与 `Ripple` 仓库并列。Python 调度器只读提取已有服务端、客户端发行包，独立编译 `java/Driver.java`。Java 驱动复用原客户端和公开消息处理器注册接口，在原处理器执行之后记录接收事件，没有修改 Ripple 源码或 POM。

入口：`sudo bash /mnt/d/Ripple/bandwidth_test/run.sh`。参数、指标和限制详见 [使用说明](../bandwidth_test/README.md)。实现计划保存在 `bandwidth_test/IMPLEMENTATION_PLAN.md`。

### 15.2 与初始方案的具体差异

- 增加订阅者侧 `peers.pcap`，覆盖原引擎 DISPATCH 引起的客户端之间转发，避免漏算本地转发流量。
- 基线通过配置中的时间边界及各抓包的 `windows.baseline` 区分，不再额外创建 baseline.pcap。
- SQLite 数据库运行在 WSL/Linux 临时目录，退出后复制到结果目录 `databases/`，避免 Windows 挂载盘同步写成本主导网络测试。
- 多订阅者串行建立连接，随后并发接收负载；探测消息可重复暖机，确保首次转发创建的回调连接已安装观测器。
- TCP 帧在截止时尚未完整传输的情况记录为 `unfinished_frames`，不等同于抓包丢包；真实缺口、损坏或截断另行标记。
- 每次保留 assets、classes、数据库和原始事件，便于复核发行包与驱动；结果目录容量需自行评估。

### 15.3 已完成的真实验收

| 场景 | 实际提交 | 成功 PUT 响应 | 唯一投递 / 预期投递 | 结果 |
|---|---:|---:|---:|---|
| 三节点、一个订阅者、256 B × 5 条/秒 × 2 秒 | 10 | 10 | 10 / 10 | 全部送达 |
| 三节点、两个订阅者、256 B × 5 条/秒 × 2 秒 | 10 | 10 | 20 / 20 | 全部送达 |
| 一个节点、四个订阅者、256 B × 5 条/秒 × 2 秒 | 10 | 10 | 40 / 40 | DISPATCH 与客户端间 SYNC 路径均验证 |
| 三节点、一个订阅者、4096 B × 20 条/秒 × 3 秒，64 kbit/s，下行排空 2 秒 | 60 | 60 | 9 / 60 | 截止仍有 51 次投递未完成，正确报告积压 |

四订阅者实验延迟 P50 约 7 ms，P95 约 9.05 ms。其结果目录为 `bandwidth_test/results/20261016-170522-204420/`。

64 kbit/s 实验中，已收到样本的 P50 约 2171 ms，P95 约 3242.8 ms。截止时整形队列积压 42890 字节、10 个包，overlimits 为 11，观察到实际排队。下行发送及排空窗口约 5.105 秒，抓包帧速率约 68.4 kbit/s；短时 HTB 突发与统计口径使其不必精确等于配置值。结果目录为 `bandwidth_test/results/20261016-170034-dd936a/`。

该低带宽结果说明“发布成功”不代表“订阅者已经收到”。51 次未完成投递是截至指定期限的观察值，不能据此断言永久丢失；延迟分位数仅覆盖已收到的 9 次投递。

早期同时建立两个订阅者连接时，原引擎 `NettyServer.findChannel()` 出现空指针异常。原服务端连接表使用 ArrayList；工具改为串行建订阅后复测通过。失败日志保留在 `results/20261016-165158-bbd7e1/`，并在使用说明中披露此引擎限制。
