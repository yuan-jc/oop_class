# 单服务端 1 KiB/s 弱网三组实验

实测日期：2026-10-22。一个服务端、一个发布客户端、一个订阅客户端。

## 条件与预期

每秒1条，发60秒，每条2048 B，共60条；正文为数字字符串（前12位序号，其余确定性随机数字），种子42。
只对服务端→订阅者限速1024 B/s＝8192 bit/s，反向和发布上传不限。TBF命令突发1600 B，内核统计为1599 B；附加延时/丢包由TBF子netem实现。
三组统一使用 `bandwidth-v0-stable`（`c9345dc2ebd10e73493a271d5f3f415c4561eca6`），原版线格式加此前共同连接修复；紧凑编码和压缩均关闭。采集脚本提交 `30dffce`。
正文输入2048 B/s，是配置出口的两倍；不计额外开销与初始突发，60条正文需要约120秒传输。因此预期停发时存在积压，实际结果还受协议头、控制流量和TCP重传影响。
延时组增加的是每个下行网络包的2秒传播延时，不是为每条消息固定总时延2秒。丢包组为网络包50%随机丢失，不是直接删除50%业务记录。

## 正确性与独立复核

统一交付与正文复核通过：`True`。三组源码、JAR及同轮正文哈希一致。
每条消息核对发送端与接收端UTF-8字节数和SHA-256，接收端另按种子/序号重新生成原文并全文比较。
统一复核脚本再次读取原始事件重算检查点与收齐时间，并只读检查两端SQLite完整性和保留正文。原版会回收旧版本，最终数据库仅保留最近若干条；数据库历史回收不计为传输丢失，全量交付正确性由逐条事件证明。

## 计量与适用边界

基础组第60秒TBF累计发送62441 B；配置速率1024 B/s，另允许1599 B初始突发，符合令牌桶口径。限速不是只约束正文净荷。
丢包发生在TBF的子netem队列，丢弃的包不应自动算作已消耗出口字节；本次不外推为某种真实卫星物理信道。
50%丢包会触发TCP拥塞控制、重传和退避；有待发数据时，限速出口也可能因等待重传而空闲。
每组只进行一轮正式运行，是指定条件的实测值，不是稳定均值或普遍恢复保证。

抓包完整性独立记录：

- base：抓包完整 `True`；告警 `[]`。
- delay：抓包完整 `False`；告警 `["TCP 序列存在缺口：('10.203.0.2', 15001, '10.203.0.1', 38388)"]`。
- loss：抓包完整 `True`；告警 `[]`。

应用日志、到达计时和正文核对独立于PCAP重组；存在抓包缺口的组，不用其PCAP宣称完整网络字节账本。原始测量状态和告警均保留，未抹除。

## 脚本与复现

```powershell
wsl -u root -- python3 /mnt/d/Ripple/bandwidth_test/slow_link_suite.py --output /var/tmp/ripple-slow-new-run --archive-to /mnt/d/Ripple/optimization_results/slow_link --size 2048 --rate 1 --duration 60 --bandwidth-bytes 1024 --delay-seconds 2 --loss-percent 50 --max-wait 1800
wsl -u root -- python3 /mnt/d/Ripple/bandwidth_test/verify_slow_link.py /var/tmp/ripple-slow-new-run
```

输出目录须使用新名称；参数和用法见 `bandwidth_test/SLOW_LINK_README.md`。默认停发后最多等1800秒，收齐可提前结束。

## 原始证据与排除记录

统一归档：`optimization_results/slow_link/verified-20261022/`。
每组保留 `config.json`、`send-end-checkpoint.json`、`slow-link-summary.json`、`per-message-integrity.csv`、两端JSONL、PCAP、tc统计、日志与数据库。顶层保留 `results.csv`、`unified-verification.json`、`selection.json` 和SHA-256清单。
第一次正式丢包尝试被人工诊断文件的jsonl后缀冲突中断，整组排除，并在相同参数下单独重跑。前两组采用原完整运行，丢包组采用完整重跑；原始尝试和失败原因保留在selection中。
原始版本在预备启动中出现连接表空指针，故正式组统一采用已保存的原版线格式稳定基线；未切换用户工作树，未引入带宽优化。
