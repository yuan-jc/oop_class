# Ripple 可视化实验控制台设计草案

状态：用户已在对话中确认，进入实现。

## 目标和使用流程

用户在 Windows 中双击“启动实验控制台”入口，程序在后台启动本地控制服务并自动打开浏览器。在网页中配置节点、各方向链路和负载，点击开始后自动构建当前 Ripple 源码、启动节点、登记订阅、确认暖机消息送达，再发送随机更新。停止生成更新后，保持节点运行指定等待时间，最终归档结果。

默认界面及说明为中文。第一版面向当前 Windows + WSL Ubuntu 环境，运行真实 Ripple JVM 和真实 Linux 流量整形。外网托管网页无法直接管理本机进程与网络，因此采用本地应用。

## 源码版本

- 当前源码目录：`D:/Ripple/Ripple`。
- 本次只读核对：工作区 HEAD 和 GitHub 上游 HEAD 均为 `468e9cb4296110467e3cfdafed412b3dbecfd52a`。
- “使用最新代码”默认指构建当前工作区实际源码，不继续沿用旧实验中的已归档发行包。源码有变化时必须重新构建；无变化可复用由相同源码摘要生成的缓存构建。
- 界面显示源码路径、HEAD、工作区变化、构建时间和产物哈希。构建失败时明确展示日志，不静默回退旧 JAR。
- 第一版不自动修改上游 ACK、重连和一致性逻辑，以便观察原有行为。外部观测适配代码与业务源码分开。

## 可选实现方式

1. 推荐：本地网页控制台 + Python 控制服务 + WSL 网络隔离和 tc + Java 实验适配器。复用已有实验资产，真实配置链路，也方便实时展示和保存结果。
2. 直接改造 Ripple 原有 Java 网页和启动流程。页面和节点耦合更深，跨节点统一管理与限速仍需要额外进程，更容易把实验控制与被测系统行为混合。

本草案采用方案 1，同时提供 Ripple 原有服务端／客户端网页入口。

## 网页功能

### 实验配置

- 添加／删除服务端、发布客户端和订阅客户端，提供单服务器、三服务器、多订阅者预设。
- 第一版支持配置多个发布者；各发布者使用独立消息标识和实验数据键，统计按发布者与序号区分。
- 每个发布者可设置 value 总字节数、每秒更新条数、发送持续秒数、随机种子。
- 全局设置暖机超时、空闲基线时间、停止发送后的固定观察秒数、应用名与数据键前缀。
- 可选择发布／订阅首连的服务端；节点间后续传播仍由所选 Ripple 协议决定。
- 优先支持前面实验使用的 hashing 协议。其他协议在界面中只展示实际已经接通并验证的选项。
- 保存／导入 JSON 配置，重复运行同一配置，保存结果用于横向比较。

### 链路配置

- 可视化拓扑与有向链路表，清楚区分 `A → B` 和 `B → A`。
- 每条有向链路独立设置带宽上限，支持 bit/s、kbit/s、Mbit/s；“不限速”独立于数字 0。
- 包含发布者到服务端、服务端间、服务端到订阅者、订阅者间的可配置链路；TCP 确认及反向响应受对应反向链路约束。
- 可设置队列字节上限，以及可选的延迟、丢包率和丢包开始／结束时间，覆盖已有短时 100% 丢包实验。
- 第一版不把 RST 作为默认故障；若提供该预设，必须独立命名、展示具体作用连接并记录注入是否生效。
- 每个运行节点位于独立命名空间，有独立实验 IP；按目的节点分类做真实整形，不用 sleep 伪装网络限速。
- 控制台访问节点原网页的管理流量不计入实验节点间限速。
- 配置链路不强制 Ripple 使用该链路；拓扑同时展示实际观察到的流量，避免把“配置了一条边”理解为“它一定承载消息”。

### 实时观测

- 阶段显示：检查环境、构建、启动、订阅、暖机、发送、等待、归档、完成／失败／取消。
- 节点列表展示角色、进程状态、实验 IP、API 端口和网页入口。
- 节点详情提供发送／接收事件列表与原始日志，支持按节点、消息类型、发布者、序号、UUID 和时间筛选。
- 发送意图、本地写入结果、消息到达、处理响应与数据库实际状态分开显示；不把写入成功或本地 ACK 当作对端落库。
- 总览展示计划／实际提交、成功发布响应、唯一送达、重复接收、截止缺失、送达延迟及积压估计。
- 使用 PCAP、原始日志和只读数据库检查补充核对，避免仅凭周期安装的客户端回调观测器得出送达结论。
- 页面只保留有界的近期记录并分页加载；原始证据写入磁盘。负载过高时明确记录观测缺口，不能将缺口当作丢消息。

### 节点网页与浏览器

- 双击入口后自动打开控制台。
- 实验就绪后自动打开各服务端／客户端的节点页面；配置中可关闭自动开标签页。
- 每个节点页面可查看本节点事件和日志，并进入原版 Ripple 网页。
- 控制台提供统一节点入口；原版页面通过本地独立端口转发访问，避免命名空间地址不可达或原页面绝对链接失效。

### 停止和结果

- “停止发送”结束负载生成并进入设定等待期；“立即结束实验”清理本次进程和网络，保留已产生的证据。
- 实验之间使用独立目录和数据库，历史结果可再次打开。
- 导出配置、节点事件 JSONL／CSV、指标 JSON／CSV、进程日志、链路 tc 状态、抓包和版本清单。
- 等待时间默认严格执行，避免因刚好收齐消息提前结束，影响对照实验窗口。
- 明确区分“实验流程完成”和“所有更新到达”。

## 本地实现边界

- 新应用位于 `D:/Ripple/ripple_lab/`，不覆盖已有 `bandwidth_test/results/` 或报告。
- 控制服务只监听本机，提供配置、构建、启动、停止、状态、分页事件、历史实验和结果下载接口。
- Windows 启动器后台启动 WSL 服务，等待可访问后再打开浏览器；不弹出不必要的辅助窗口。
- 使用当前可用的 Python、Java、Maven、iproute2、tc 和 tcpdump。网页以本地静态资源交付，不依赖外部 CDN。
- 构建和实验文件隔离，网络与进程清理只针对本次创建的资源。
- 启动、订阅和观测初始化有超时；失败时停止进入后续负载阶段，保留错误和现场信息。

## 验收标准

1. 双击启动入口后可在浏览器打开中文控制台，能保存和回读配置。
2. 修改某个方向的带宽不改变反向或其他目的节点的配置；通过 tc 配置和实际流量核验。
3. 使用当前源码成功构建并启动至少 1 服务端、1 发布者、1 订阅者；订阅和暖机自动完成。
4. 正式发送的 value 字节数准确、种子可复现；区分设定速率与实际提交速率，不用无限突发追赶漏掉的调度时隙。
5. 至少完成正常、限速积压、短时丢包三个端到端实验；页面、原始事件和数据库／抓包检查相互核对。
6. 服务端和客户端各有可打开的节点页面，能查看真实发送／接收记录及原版网页。
7. 多发布者序号不冲突，多订阅者送达按目标分别统计。
8. 取消、异常退出和重新运行后，本次资源清理、历史证据保留，不影响其他 Ripple 实例。
9. 界面和接口通过本地浏览器验证；若环境不支持某项验证，交付时明确标出，不冒称通过。
