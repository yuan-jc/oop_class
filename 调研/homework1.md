# 服务化之后的软件发展新特征与智能化趋势研究

## 摘要

服务化通过标准接口和网络调用提高了软件能力的复用程度，但跨系统任务的理解、规划与异常处理仍较多依赖开发者预设流程或用户手动操作。近年来，大语言模型与工具调用、外部知识检索和执行反馈相结合，使软件能够在给定目标与权限边界内动态组织部分执行过程。本文在课程所给软件发展阶段框架的基础上，从控制流、接口、状态管理、软件生产、可靠性及成本六个维度分析这一变化，并结合代表性技术与企业案例讨论其产业意义。研究认为，将“智能化”视为服务化之后的重要发展方向具有技术依据，但将其判定为已经全面成熟的新阶段仍需谨慎。其关键变化在于，软件开始把部分任务规划与服务编排交给模型，同时依靠确定性程序、权限机制和人工监督保证执行边界。智能体由此成为连接用户目标与既有软件能力的一种新抽象，而面向对象与服务化仍构成其工程基础。

关键词：软件演化；服务化；大语言模型；智能体；面向对象；软件工程

## 一 研究背景与阶段划分依据

课程材料将软件的发展概括为独立化、产品化、结构化、对象化、网络化和服务化六个阶段。这一框架提供了理解软件演化的视角：软件通过不断调整抽象方式和系统边界，逐步降低开发、复用及协作成本。例如，对象化将状态与行为封装在对象内部，服务化则进一步通过接口契约，使调用者能够使用跨进程、跨网络的业务能力。这些阶段并非彼此排斥，后出现的技术通常建立在既有技术之上。

沿用这一分析思路，判断服务化之后是否出现新的发展阶段，不能只依据产品热度或技术名称，而应考察软件组织方式是否发生了持续变化。本文采用三个判断维度：软件承担的任务边界是否扩大，开发者组织系统的核心抽象是否变化，以及支撑这种变化的工具与工程方法是否逐步形成。

服务化解决了“能力如何被封装和调用”的问题，却没有自动解决“为实现目标应调用什么能力”的问题。以差旅安排为例，机票、酒店和报销系统即使都提供 API，用户仍需比较约束、选择方案；若希望自动完成，开发者通常需要提前编写流程。大语言模型则使系统能够从自然语言中提取目标与约束，并结合工具返回的信息调整后续操作。这意味着，部分原本由人承担的服务选择与编排工作开始进入软件系统内部。

不过，智能体、规划和机器学习都早于生成式 AI 存在。当前趋势的新意，在于通用语言模型将自然语言交互、知识处理与工具选择结合起来，并通过软件接口接入不同任务环境。因此，本文将“智能化”界定为一种正在形成的软件发展方向：系统在明确约束下，依据目标和环境反馈动态选择部分行动，并接受外部检验与必要的人类干预。这一定义强调可观察的系统行为，不预设软件具有人的意识或通用自主能力。

本文采用文献分析与案例比较方法，以 2022—2025 年的代表性研究和产品实践为主要观察对象，并核对公开技术文档。学术论文用于说明方法及实验结果，官方文档用于确认产品能力和设计路线；由案例推导出的阶段判断属于本文分析，不等同于行业共识或市场份额结论。

## 二 智能化阶段的技术特征

### 1 控制流扩展为目标驱动的反馈闭环

传统业务软件通常由开发者规定主要执行路径，运行时根据输入和状态选择分支。智能体系统则允许模型在运行时决定部分工具调用及其顺序。Yao 等提出的 ReAct 方法将推理过程与行动交替组织，使模型能够获取外部信息，并据此更新计划、处理异常。[1] 这一机制为“理解目标—采取行动—观察结果—调整行动”的闭环提供了具体方法依据。

这种动态性需要与预设工作流区分。Anthropic 的工程文档将工作流描述为沿预定义代码路径组织模型和工具的系统，将智能体描述为由模型动态指导过程与工具使用的系统。[2] 因而，在固定流程中加入一个文本生成节点，并不意味着整个系统已经具有自主规划能力。模型参与决策的范围及其是否利用执行反馈，是更有区分度的判断标准。

这里发生变化的是部分任务层控制权，而非所有程序逻辑。例如，系统可以根据预算和时间约束选择查询哪些航班，但支付金额校验、账户权限和交易一致性仍应由明确规则保障。较为可行的架构是让模型处理开放性的选择问题，让确定性组件执行受约束的业务操作，并为高影响行动设置确认与中止条件。

### 2 软件接口增加了面向智能体的语义要求

服务化以 API 契约连接不同系统，调用方通常由开发者事先编写。智能体作为新的调用方，除参数类型外，还需要理解工具的用途、适用条件、返回结果和潜在副作用。例如，“查询订单”与“取消订单”可能具有相似的参数，却需要完全不同的权限和确认机制。

Anthropic 于 2024 年 11 月发布的模型上下文协议（Model Context Protocol，MCP），通过统一连接方式帮助 AI 应用访问数据源与工具，减少重复编写专用集成的负担。[3] MCP 的意义在于推动连接方式标准化；它本身并不保证模型能够正确选择工具，也不会自动赋予调用权限。因此，协议兼容、语义清晰和访问控制必须共同设计。

从软件工程角度看，接口设计的评价标准随之扩大：除了“程序能否调用”，还要考虑“模型能否在正确条件下调用”。清楚的工具说明、结构化输入输出、可辨识的错误信息和最小权限，有助于减少误用。即使系统通过图形界面操作既有软件，也仍需处理页面变化、执行失败和权限检查等问题。

### 3 上下文成为影响运行行为的重要状态

智能软件的行为不仅取决于代码、数据与模型参数，还取决于本次执行获得的上下文。用户目标、历史对话、检索材料、工具返回值和当前任务进度，都可能改变后续决策。因此，如何选择、更新和隔离这些信息，成为独立的工程问题。

Lewis 等提出的检索增强生成（Retrieval-Augmented Generation，RAG）将模型的参数化知识与外部检索结合，为知识密集型任务提供了方法基础。[4] 在实际应用中，这类机制使系统能够参考企业制度、产品手册或项目代码，而无需仅依赖模型训练时保存的知识。但检索结果可能过期、不完整或包含错误，提供来源也不等于模型一定正确使用了来源。

由此，上下文管理需要回答具体问题：哪些资料与当前目标相关，信息是否最新，用户是否有权访问，不同来源冲突时如何处理，以及历史状态何时失效。上下文越长并不必然越好，冗余内容会增加成本，也可能干扰判断。持久化任务状态与模型输入还应分别管理，避免把一段可能被截断的对话记录当作可靠的业务账本。

### 4 软件生产由代码辅助扩展到任务代理

智能化也直接作用于软件开发过程。代码补全主要辅助局部表达，而编程智能体可以围绕任务描述搜索仓库、修改文件、执行测试，再根据反馈继续调整。SWE-bench 将真实 GitHub 问题与对应代码仓库构造成评测任务，其原始数据集包含来自 12 个 Python 仓库的 2294 个问题，要求系统通过代码修改解决问题。[5] 这类评测把关注点从“生成一段看似合理的代码”推进到“在已有项目中完成可验证的变更”。

斯坦福《2025 AI Index》报告摘要指出，SWE-bench 的相关性能指标在一年间提高了 67.3 个百分点。[6] 这一趋势说明模型系统处理工程任务的能力有所增强，但不能据此认定同等比例的真实开发工作已经能够自动完成。比较结果时，还需区分数据集版本、可用工具、尝试次数与计算预算；通过给定测试，也不保证代码满足全部需求和长期维护要求。

实际生产率还受到项目熟悉程度和审查成本影响。METR 的一项随机对照研究让 16 名具有成熟项目经验的开源开发者完成 246 项任务，发现允许使用 2025 年初的 AI 工具后，完成时间平均增加了 19%。[7] 该结论针对特定工具、开发者和任务环境，不能推广为“AI 对所有开发者都无效”；但它表明，能力评测的进步不能直接替代真实工作场景中的效率测量。

因此，更稳妥的判断是：编程智能体扩大了可委托给软件的实现范围，而需求澄清、架构设计、验收标准和代码评审的重要性仍然存在。其价值应通过任务完成质量、总耗时、缺陷与返工情况衡量。

### 5 可靠性工程需要覆盖模型决策与行动后果

传统软件也存在并发、外部依赖和输入不确定性，不能简单概括为“完全确定”。智能体新增的挑战是，模型对目标与材料的解释具有不确定性，这种不确定性又会进入工具选择和多步执行过程。同一任务即使每一步大多正确，也可能因多次决策累积而失败。

作为简化说明，若假设十个步骤相互独立，且每一步成功率均为 95%，则全部成功的概率约为 59.9%。这一数值只是数学示例，真实步骤通常存在依赖，不能据此估算某一产品的可靠性；它说明设计者必须关注完整任务的结果，而不能只检查单次回答。

OpenAI Agents SDK 将工具、交接机制、校验机制及执行追踪列为框架能力。[8] 这些设计反映出智能体工程对过程可观测性和边界控制的需求。不过，记录完整执行轨迹只是诊断基础，不能自动证明决策正确。系统还需针对真实任务建立评测集，覆盖错误工具调用、检索失败、目标歧义与越权尝试等情形。

安全问题同样进入控制流。外部网页或文档中的内容可能被模型误当成行动指令，因此“可供参考的数据”与“具有授权效力的指令”必须区分。业务系统应在执行端验证身份与权限，并限制可访问资源、操作次数和执行时间；对不可轻易撤销的操作，保留人工确认或其他独立校验。可靠性最终体现为能否发现错误、限制损失并恢复任务，而非仅仅生成流畅的解释。

### 6 成本优化转向完整任务的质量与资源权衡

智能体一次任务可能触发多轮推理、检索和工具调用，其资源消耗与执行路径相关。较强模型或更长推理过程可能改善复杂任务表现，却也可能增加延迟和费用。Anthropic 的工程文档因此建议从简单方案开始，仅在任务收益足以支撑额外复杂度时引入智能体。[2]

推理价格下降也不能直接等同于业务任务成本下降。《2025 AI Index》指出，达到 GPT-3.5 水平的系统推理成本在 2022 年 11 月至 2024 年 10 月间下降超过 280 倍。[6] 这一结果反映特定能力水平下的成本趋势，并不表示任意智能体任务的总成本都按同一比例下降。更复杂的调用链和更多重试可能抵消单次推理的节省。

因此，成本评估宜同时考虑模型调用、工具执行、人工复核与失败返工。缓存、任务路由、上下文压缩和大小模型协作都是可能的优化手段，但应检验其是否损害质量。对于流程固定、规则明确的任务，直接使用普通程序或预设工作流，可能具有更好的成本与可靠性表现。

## 三 代表性企业与产品路线

判断企业的代表性，应考察其体现了哪一种技术路线。下述案例覆盖模型、工具协议、开发框架和应用平台，目的在于比较不同层次的贡献，不构成企业实力排名。

### 1 OpenAI 与 Anthropic 的框架和协议路线

OpenAI Agents SDK 将模型、工具、交接与执行追踪组织为可复用的开发框架。[8] 其代表性在于，智能应用开发开始具备超出单次模型调用的系统构件：开发者需要管理执行过程、观察工具调用，并在必要时介入。本文据此认为，智能体的竞争不仅发生在模型能力层，也发生在支持模型执行任务的工程框架层。

Anthropic 的 MCP 和智能体工程实践则分别体现接口标准化与架构方法的探索。[2][3] 前者降低连接外部数据和工具时的重复集成成本，后者明确区分预设工作流与动态智能体，并强调环境反馈和停止条件。两家公司的案例共同说明，模型能力只有与工具、状态和约束机制结合，才能形成可运行的软件系统；框架或协议的存在则不能单独证明业务成效。

### 2 Anysphere 的编程应用路线

Anysphere 的 Cursor 代表以软件开发环境为入口的应用路线。METR 研究中的参与者主要使用 Cursor Pro 与 Claude 3.5/3.7 Sonnet，说明在这一具体实践中，编辑器产品与基础模型由不同主体提供。[7] 这为分析应用层与模型层的分工提供了实际案例。

对这类产品而言，应用价值不仅取决于模型本身，还取决于代码上下文的组织、修改过程与开发者审查方式。成熟代码库包含未完全写入文档的约定，开发者接受建议前还需理解并验证变更。因此，其代表性是把 AI 融入实际开发过程，而不是已经证明所有编程任务都获得稳定提速。

### 3 DeepSeek 与阿里巴巴的开放模型路线

DeepSeek-R1 及其官方仓库展示了强化学习与推理能力训练的结合，并提供模型权重及蒸馏模型。[9][10] 需要区分的是，R1-Zero 探索了无前置监督微调的强化学习路线，而 R1 引入冷启动数据及多阶段训练流程，不能将两者概括为完全相同的方法。[10]

开放权重为研究者和企业提供了本地部署、进一步适配与实验比较的选择。但开放权重不等于训练数据和全部训练过程公开，也不意味着部署成本可以忽略。DeepSeek 的案例更直接支持的判断是，较强推理模型的获取方式趋于多样化，应用开发者因此拥有更多架构选择；“整体成本必然最低”则需要额外的同口径比较。

阿里巴巴于 2025 年 7 月发布的 Qwen3-Coder 将仓库级上下文、多轮工具交互和执行反馈纳入其技术路线，并同步提供 Qwen Code 命令行工具。[11] 其意义在于，代码模型的训练目标正在从局部代码生成扩展到与环境交互的任务求解。代码执行和测试可以提供较明确的反馈，这也解释了软件开发为何成为智能体的重要应用场景。官方公布的模型成绩仍应与独立评测及实际项目效果区分。

### 4 字节跳动的智能体开发平台路线

字节跳动的 Coze Studio 将提示词、知识库、插件与工作流组织为可视化开发平台，并提供开源实现。[12] 与直接面向终端用户的单一智能体相比，这一路线更关注构建、调试和部署智能应用的门槛。平台把常见组件组合为可复用资源，使开发者能够围绕业务流程配置应用。

Coze Studio 的官方说明同时列出了微服务架构与领域驱动设计等技术基础。[12] 这一案例说明智能化与此前的软件工程方法具有连续性。可视化配置可以降低部分编码工作量，但需求定义、权限设置、知识质量和上线评测仍需要工程判断，低代码不等于低治理成本。

综合这些案例，可以将相关能力分析为模型层、执行与连接层、应用层。该分层是理解技术分工的分析工具，各企业通常跨越多个层次。模型层提供推理和生成能力，执行与连接层管理工具及状态，应用层将这些能力组织为具体任务。产业竞争因而可能同时围绕模型质量、连接生态和业务完成效果展开。

## 四 与面向对象方法的关系及阶段判断的边界

从面向对象程序设计的视角看，智能体并未使对象失去意义。对象通过封装保护状态，通过接口约束行为；智能体也需要借助这些机制管理任务状态、调用工具并隔离外部依赖。例如，可以由订单对象维护合法状态转换，由支付服务保证扣款规则，由智能体决定何时查询订单或提交候选方案。模型决定调用意图，业务对象和服务仍负责维护不变量。

二者的重要差异在于行为选择方式。普通对象的方法行为主要由程序实现约定，而智能体可能依据模型输出，在多个可用行动之间进行动态选择。因此，在系统设计中引入智能体后，封装、接口契约和依赖管理仍然适用，但还需要把模型选择的结果视为待校验输入。清晰的模块边界能够防止一次错误判断直接演变为任意业务操作。

服务化与智能化也存在相似的承接关系。服务提供可复用能力，智能体利用这些能力处理目标表达较开放、执行步骤难以完全预设的任务。如果缺少稳定的服务接口、准确的数据和明确的业务规则，模型很难单独弥补这些基础问题。因此，软件发展更可能呈现多种方法共存的形态。

将“智能化”判断为成熟阶段，还需要比产品发布更强的证据：在不同任务和较长运行周期内，系统能否保持质量；考虑人工审查和返工后，是否仍有合理的成本收益；发生错误时，是否能够追溯并限制影响。本文所用文献与案例能说明技术方向正在形成，但不足以证明这些条件已在整个软件行业普遍满足。

## 五 结论

本文认为，“智能化”可以作为服务化之后软件发展的重要趋势加以概括。其技术依据是，模型开始参与部分运行时决策，利用外部工具与环境反馈推进任务；与之相应，接口语义、上下文管理、任务评测和资源预算逐步成为系统设计的重要内容。代表性企业的实践进一步表明，这种变化已涉及模型、开发框架、连接协议和应用平台等多个层次。

这一判断应保留适用边界。智能体的动态能力需要与确定性规则配合，基准成绩需要接受真实生产率检验，模型开放性也不能替代对部署成本和数据治理的分析。更有说服力的阶段标准是：软件是否能够在给定目标和权限范围内，持续、可验证地完成具有一定开放性的任务，并且其整体收益足以承担引入的复杂度。

对面向对象程序设计课程而言，这一趋势提示我们：未来的软件开发可能减少对部分实现步骤的手工描述，却会更加依赖清晰的抽象、稳定的接口、可靠的状态约束和可检验的需求。对象、服务与智能体分别在不同层次组织软件能力，共同构成智能化软件的工程基础。
